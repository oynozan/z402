# z402 Server Side Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the z402 facilitator, server scheme, paid API route, lightwalletd client and Rust decryptor, so that a stock x402 v2 client streams paid calls against one shielded testnet deposit per window.

**Architecture:**
- **Facilitator:** an x402 v2 facilitator (`x402Facilitator` + `PrepaidVoucherFacilitatorScheme`) behind Express on 127.0.0.1:4022.
  - It keeps sessions and deposits as event-sourced in-memory state, with a JSONL ledger written synchronously at settle time.
  - It looks deposits up with grpc-js `GetTransaction` on testnet.zec.rocks and trial-decrypts them with the `zdecrypt` CLI, which receives the merchant UIVK through its environment.
  - A 5 s tip-driven watcher moves deposits through `pending → confirmed → final`, or to `orphaned` / `dead`.
- **Paid API:** an Express app with `@x402/express` middleware and our `PrepaidVoucherServerScheme` serves one route, `/chunk`.

**Tech Stack:**
- Node 26, TypeScript (strict, ESM, NodeNext), pnpm workspace, vitest.
- express 5.3.0, `@x402/core` / `@x402/express` / `@x402/fetch` 2.28.0.
- `@grpc/grpc-js` and `@grpc/proto-loader`.
- Rust (≥ 1.89) with the stable librustzcash line (`zcash_primitives` 0.31.0).

**Spec:**
- [`docs/superpowers/specs/2026-10-27-z402-facilitator-design.md`](../specs/2026-10-27-z402-facilitator-design.md): the design. It cites "design §n" throughout.
- [`docs/spec/mvp-build-doc.md`](../../spec/mvp-build-doc.md): the source spec.

## Review Focus

These are inputs and failure modes the spec implies but no other test exercises. Each has a test in the owning task:

1. **A real zingo-cli deposit rather than fixtures.** A v6 Ironwood output to payTo with a text memo `"<sessionKey>:<n>"` and expiry about tip + 120 must decrypt with `toPayTo: true` and earn zero-conf credit. → Task 12, step 5 assertions.
2. **lightwalletd that answers slowly (4 s per RPC) on the depositing call.** `/verify` must still return within `depositWaitMs` plus one RPC, and therefore under the API's 30 s `HTTPFacilitatorClient` timeout. → Task 8 test `slow chain still answers within budget`.
3. **A `depositTxid` presented in uppercase or with surrounding whitespace.** It must be refused as `invalid_payload` and never credited a second time under another spelling. → Task 8 test `txid spelling variants are rejected`.
4. **A facilitator restart while a deposit is pending.** After replay, the watcher must re-inspect at once, so the deposit confirms without waiting for a client call. → Task 9 test `startFacilitator polls once at start`, and Task 11 restart scenario.
5. **Two in-flight calls from one session, both carrying the same new `depositTxid`.** The deposit is credited exactly once, and both settles ack it or one fails cleanly. → Task 8 test `concurrent settles with one new deposit credit once`.

```ts
export interface DepositRecord {
  txid: string; sessionKey: string; valueZat: bigint; zeroConf: boolean;
  expiryHeight: number; firstSeenTip: number;
  status: DepositStatus; minedHeight: number | null; confirmations: number;
  notFound: { count: number; sinceMs: number } | null; deadAtTip: number | null;
}
export type Evaluation =
  | { ok: true; valueZat: bigint; zeroConf: boolean; status: DepositStatus; minedHeight: number | null; confirmations: number; expiryHeight: number }
  | { ok: false; code: "z402_deposit_transparent" | "z402_deposit_not_to_merchant" | "z402_deposit_memo_mismatch" | "z402_deposit_dead" };
export const NOT_FOUND_DEAD_COUNT = 3, NOT_FOUND_DEAD_MS = 60_000, DEAD_RECHECK_BLOCKS = 20, SNAPSHOT_FINAL_KEEP = 4;
export function evaluateDeposit(insp: FoundInspection, sessionKey: string, terms: Terms, tip: number): Evaluation;
export function observe(rec: DepositRecord, obs: TxInspection, tip: number, nowMs: number): DepositRecord; // pure; new object
export function buildSnapshot(a: { sessionKey: string; cumulativeZat: bigint; deposits: DepositRecord[]; terms: Terms; tip: number }): SessionSnapshot;
```

`evaluateDeposit` rules, applied in order:
1. Any transparent part gives `deposit_transparent`.
2. No outputs gives `deposit_not_to_merchant`.
3. Sum the outputs whose `parseDepositMemo(memo)?.sessionKey === sessionKey`; if none match, `deposit_memo_mismatch`.
4. If `isDepositDead({ minedHeight, expiryHeight, tip })`, `deposit_dead`.
5. Status comes from location: mempool → pending; mined with `confirmations(h, tip)` ≥ `FINAL_CONFIRMATIONS` → final, otherwise confirmed; orphaned → orphaned.
6. `zeroConf = zeroConfEligible({ valueZat, expiryHeight, referenceTip: tip, terms })`.

`observe` implements the table in design §4.1, plus these rules:
- A not-found answer increments `notFound` without changing status. It sets `dead` once `count >= 3` and `nowMs - sinceMs >= 60_000`.
- Any found answer resets `notFound`.
- A `dead` record is promoted to `confirmed` only when it is found mined and `tip - deadAtTip <= 20`.
- `zeroConf`, `valueZat` and `firstSeenTip` never change.

Algorithm (design §4.3 and §4.4). These are the decisions the tests pin:
- **Requirements and payload checks**, in order:
  1. The requirements must equal the config exactly: `scheme`, `network`, `asset`, `payTo`, `amount === String(priceZat)`, and `parseTerms(extra)` deep-equal to `config.terms`. Otherwise `invalid_payment_requirements`.
  2. `payload.x402Version !== 2` gives `invalid_x402_version`.
  3. `payload.accepted.scheme` differing gives `invalid_scheme`; a differing `network` gives `invalid_network`.
  4. `parseVoucherPayload` throwing gives `invalid_payload`.
  5. A bad signature gives `z402_invalid_signature`, **with no snapshot**, because the caller is unauthenticated.
- **Snapshots:** every refusal after the signature check carries `extra.session`, the projected snapshot.
- **Deposits:**
  - The projected deposit set is the session's credited deposits plus the presented txid's resolved `Evaluation`, if it is ok and not yet credited.
  - A presented txid that is already credited to this session is a no-op.
  - An owner other than this session gives `z402_deposit_other_session`.
  - A recorded `dead` txid gives `z402_deposit_dead`.
  - `found` plus a failed evaluation returns that evaluation's code.
  - Resolver `not_found` gives `z402_deposit_not_found`; `unavailable` gives `z402_chain_unavailable`.
- **Lazy crediting:** if the voucher fits without the presented deposit, call `resolver.startBackground(txid, depositWaitMs)` and return valid without awaiting. Otherwise `await resolver.lookup(txid, depositWaitMs)`.
- **Refresh before refuse:** if the voucher still does not fit and a live pending deposit exists, `await watcher.refreshSession(key)` and recompute.
- **Settle** uses `resolver.peek` only and never awaits the chain. After its last check it calls `commit([...depositEventIfNew, { t: "voucher", ... }])` synchronously, then calls `resolver.forget(txid)`.
  - The deposit event's `firstSeenTip` is the lookup's `tip`.
  - The reply's `transaction` is the txid if it is credited to this session (new or existing), otherwise `""`.
  - `amount = String(c_new - c_last)`, `payer = sessionKey`.

Implementation decisions:
- An empty `facilitatorUrl` throws `/facilitatorUrl/`; the SDK would fall back to x402.org.
- `HTTPFacilitatorClient({ url, timeoutMs: 30_000, createAuthHeaders })`, where `createAuthHeaders` returns `{ verify, settle, supported }`.
- `x402ResourceServer(client).register(NETWORK, new PrepaidVoucherServerScheme({ payTo }))`.
- Routes are typed as `RoutesConfig`, keyed `"/chunk"` (verb-less), with `{ accepts: { scheme: SCHEME, network: NETWORK, price: { amount: String(priceZat), asset: ASSET }, payTo, maxTimeoutSeconds: 60 }, mimeType: "application/json" }`.
- Middleware: `const http = new x402HTTPResourceServer(server, routes); await http.initialize(); app.use(paymentMiddlewareFromHTTPServer(http, undefined, undefined, false))`.
- The handler decodes the voucher with `decodePaymentSignatureHeader` from `@x402/core/http`.
- `main.ts` reads `Z402_FACILITATOR_URL` (required), `Z402_FACILITATOR_TOKEN`, `Z402_PAY_TO`, `Z402_PRICE_ZAT` (500), and `Z402_API_HOST` / `Z402_API_PORT` (`127.0.0.1` / `4021`).

`TestClientScheme` is test-only; the real client is z402-08's. It is a `SchemeNetworkClient`:
- `findDefaultAsset("ZEC", "zcash:*")` → `{ asset: "ZEC", decimals: 8, symbol: "ZEC" }`.
- `createPaymentPayload(v, req)` returns `{ x402Version: v, payload }`, where the payload signs `c = synced + BigInt(req.amount)` and attaches `pendingTxid` until acked.
- `schemeHooks.onPaymentResponse`:
  - on success, sync `c` from `extra.session.cumulativeZat` and clear `pendingTxid` once `transaction === pendingTxid`;
  - on a `z402_cumulative_mismatch` corrective 402, resync and return `{ recovered: true }`.
- The exact hook context type is in `docs/research/x402-e2e-spike.md` §7.
